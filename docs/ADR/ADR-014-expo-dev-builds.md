# ADR-014 — Expo development builds, EAS and Continuous Native Generation

Status: Proposed · 2026-10-02

## Context
The app needs native capabilities: maps with a Google Maps key on Android, push notifications (Expo's setup guide uses development builds and EAS-managed credentials), camera scanning, secure storage, and a payment SDK or hosted-page flow. Expo Go is not sufficient for a production app of this kind.

## Decision
- Use **Expo development builds** from day one (`expo-dev-client`), built with **EAS Build** (cloud) — this also covers the missing local Android SDK on the current dev machine.
- **Continuous Native Generation:** `ios/` and `android/` are generated by `expo prebuild` from `app.config.ts` and config plugins, not committed (already in `.gitignore`).
- Build profiles: `development`, `preview` (internal distribution for staging), `production`.
- **EAS Update** for JavaScript-only fixes, pinned to runtime versions, with staged rollouts; native changes go through store review.
- New Architecture as provided by Expo SDK 57 defaults; libraries chosen must support it (verified at install time).

## Alternatives
- **Bare React Native** — full control, more native maintenance.
- **Committed native folders** — needed only if we must patch native code by hand; config plugins are preferred.

## Consequences
- ✅ Reproducible native projects; fewer merge conflicts; OTA fixes possible.
- ⚠️ EAS usage has a cost tier above the free plan for frequent builds — confirm budget with the client.
- ⚠️ Requires Apple Developer and Google Play accounts owned by the client (D9).
